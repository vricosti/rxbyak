rxbyak vs xbyak — Comprehensive Differences
==============================================

rxbyak is a Rust port of xbyak (https://github.com/herumi/xbyak), the C++
x86/x64 JIT assembler. While the encoding logic and instruction coverage are
faithful to xbyak, the Rust language imposes different idioms for ownership,
error handling, type safety, and polymorphism.

This document lists every known API and design difference.


1. 64-BIT ONLY
---------------
xbyak supports both 32-bit (XBYAK32) and 64-bit modes.
rxbyak is 64-bit only.

Why: 32-bit JIT is rarely needed in modern contexts. Dropping it simplifies
the entire encoder and avoids carrying two code paths. The following xbyak
preprocessor defines have no rxbyak equivalent:

  XBYAK32, XBYAK64, XBYAK64_WIN, XBYAK64_GCC,
  XBYAK_USE_OP_NAMES, XBYAK_ENABLE_OMITTED_OPERAND,
  XBYAK_UNDEF_JNL, XBYAK_NO_EXCEPTION, XBYAK_USE_MEMFD,
  XBYAK_OLD_DISP_CHECK

Rust's cfg() attributes replace preprocessor-based feature gating.


2. ERROR HANDLING: Result<()> INSTEAD OF EXCEPTIONS
----------------------------------------------------
xbyak throws Xbyak::Error exceptions (or uses error codes with
XBYAK_NO_EXCEPTION). rxbyak uses Rust's Result<T, Error> pattern:

  // xbyak (C++)
  mov(eax, ecx);                // may throw

  // rxbyak (Rust)
  asm.mov(EAX, ECX)?;           // ? propagates errors

Every instruction method returns Result<()>. The Error enum has 54 variants
that map 1:1 from xbyak's error codes.

Why: Rust has no exceptions. Result is idiomatic and forces callers to handle
errors, eliminating the possibility of silent encoding failures.


3. IMMEDIATE TYPES: u8 INSTEAD OF int
---------------------------------------
xbyak uses C++ int (32-bit signed) for most immediates, including shift
counts and imm8 operands. rxbyak uses precise Rust integer types:

  Shift/rotate immediates (shl, shr, sar, rol, ror, rcl, rcr): u8
  Bit test immediates (bt_imm, bts_imm, btr_imm, btc_imm):     u8
  SSE/AVX imm8 operands (codegen-generated):                     u8
  General immediates (mov, add, sub, etc.):                       i64 (via RegMemImm)
  push_imm:                                                       i32
  ret_imm:                                                        u16
  enter:                                                          u16, u8

Why: Rust's strict typing forces explicit choice of integer width. Using u8
for shift counts and imm8 operands prevents out-of-range values at compile
time. xbyak's int would silently truncate; rxbyak makes the constraint
explicit.


4. NO FUNCTION OVERLOADING — SUFFIXED METHOD NAMES
----------------------------------------------------
C++ allows multiple functions with the same name but different parameter
types. Rust does not. Where xbyak uses overloading, rxbyak uses distinct
method names with suffixes:

  xbyak                         rxbyak
  ─────────────────────────────────────────────────
  push(reg)                     push(reg)
  push(imm)                     push_imm(imm)
  ret()                         ret()
  ret(imm)                      ret_imm(imm)
  jmp(label)                    jmp(&label, JmpType)
  jmp(reg)                      jmp_reg(op)
  call(label)                   call(&label)
  call(reg)                     call_reg(op)
  shl(op, imm)                  shl(op, imm)
  shl(op, cl)                   shl_cl(op)
  sar(op, imm)                  sar(op, imm)
  sar(op, cl)                   sar_cl(op)
  bt(op, reg)                   bt(op, reg)
  bt(op, imm)                   bt_imm(op, imm)
  adcx(d, reg, op)              adcx3(d, reg, op)
  adox(d, reg, op)              adox3(d, reg, op)
  bndmov(mem, bnd)              bndmov_store(mem, bnd)
  shld(op, reg, imm)            shld(op, reg, imm)
  shld(op, reg, cl)             shld_cl(op, reg)
  pslld(xmm, xmm)              pslld(xmm, xmm)          [SSE register form]
  pslld(xmm, imm)              pslld_imm(xmm, imm)      [immediate form]
  movhps(xmm, mem)             movhps_load(xmm, mem)
  movhps(mem, xmm)             movhps_store(mem, xmm)
  mov(reg, label)               lea_label(reg, &label)

The Into<RegMem> / Into<RegMemImm> trait bounds provide some overloading
for operands that differ only in type (Reg vs Address vs i32), but not
for fundamentally different encodings.


5. RUST KEYWORD ESCAPES
-------------------------
x86 mnemonics that collide with Rust keywords get an underscore suffix:

  xbyak      rxbyak       Reason
  ──────────────────────────────────
  and        and_         Rust keyword
  or         or_          Rust keyword
  not        not_         Rust keyword
  xor        xor_         Rust keyword
  std        std_         Rust standard library name
  in         in_          Rust keyword (if ever added)
  loop       loop_        Rust keyword (if ever added)
  mod        mod_         Rust keyword (if ever added)

Additionally, movsd (string operation) is renamed to movsd_string() to
avoid collision with the SSE movsd instruction which keeps the name movsd().


6. FLAT Reg STRUCT INSTEAD OF CLASS HIERARCHY
----------------------------------------------
xbyak uses a deep C++ class hierarchy:
  Operand -> Reg -> Reg8/Reg16/Reg32/Reg64 -> Xmm/Ymm/Zmm/Mmx/...

rxbyak replaces it with a single flat struct:

  pub struct Reg {
      idx: u8,
      kind: Kind,        // enum: Reg, Xmm, Ymm, Zmm, Mmx, Fpu, Opmask, Tmm, ...
      bit: u16,          // 8, 16, 32, 64, 128, 256, 512
      mask: u8,          // EVEX writemask index
      rounding: Rounding,
      zero: bool,        // EVEX zeroing
      nf: bool,          // APX NF
      zu: bool,          // APX ZU
  }

Reg derives Clone + Copy, so register values are always cheaply copied
(no ownership transfer). The kind field + helper methods (is_xmm(),
is_reg(), etc.) replace virtual dispatch.

Why: Rust has no class inheritance. A flat struct with a kind discriminant
is idiomatic, avoids dynamic dispatch, and enables Copy semantics.


7. REGISTER CONSTANTS: UPPER_CASE
-----------------------------------
xbyak defines registers as lowercase global objects:  eax, xmm0, rsp
rxbyak uses Rust const items in UPPER_CASE:           EAX, XMM0, RSP

  pub const EAX: Reg = Reg::gpr32(0);
  pub const XMM0: Reg = Reg::xmm(0);
  pub const RSP: Reg = Reg::gpr64(4);

Why: Rust convention requires UPPER_CASE for const items. The compiler
warns on lowercase constants.


8. EVEX MODIFIERS: METHOD CHAINING INSTEAD OF OPERATOR|
---------------------------------------------------------
xbyak uses bitwise OR for EVEX writemask, zeroing, and rounding:

  vaddps(zmm0 | k1 | T_z, zmm1, zmm2);
  vaddps(zmm0 | k1 | T_rn_sae, zmm1, zmm2);

rxbyak uses method chaining:

  asm.vaddps(ZMM0.k(1).z(), ZMM1, ZMM2)?;
  asm.vaddps(ZMM0.k(1).rounding(Rounding::RnSae), ZMM1, ZMM2)?;

Modifier methods return a modified copy of the register:
  .k(mask_idx)              — set writemask
  .z()                      — enable zeroing
  .rounding(Rounding::*)    — set rounding mode
  .nf()                     — APX NF flag
  .zu()                     — APX ZU flag

Why: Rust's BitOr trait could work but requires a wrapper type for each
modifier kind. Method chaining is clearer and provides type-safe access.


9. MEMORY ADDRESSING: FREE FUNCTIONS INSTEAD OF operator[]
------------------------------------------------------------
xbyak uses AddressFrame objects with operator[]:

  mov(eax, dword[rbx + rcx*4 + 8]);

rxbyak uses free functions taking RegExp arguments:

  asm.mov(EAX, dword_ptr(RBX + RCX * 4 + 8))?;

Address expression operators (Add, Sub, Mul on Reg/RegExp) build RegExp
values, then ptr()/dword_ptr()/qword_ptr()/etc. wrap them into Address.

Note: operator overloads on RegExp panic (via .expect()) on invalid
addressing, since Rust's Add trait cannot return Result. This is a
deliberate ergonomics trade-off.


10. LABEL API DIFFERENCES
---------------------------
xbyak:
  Label label;
  jmp(label);            // forward reference, auto-detect jump type
  L(label);              // define label

rxbyak:
  let label = asm.create_label();
  asm.jmp(&label, JmpType::Near)?;    // explicit JmpType required
  asm.bind(&label)?;                   // bind, not L()

Key differences:
  - Labels are opaque handles (just a LabelId(u32)), not objects with state.
    All state is in LabelManager.
  - Jump type must be explicit: JmpType::Short, JmpType::Near, or
    JmpType::Auto. xbyak auto-detects by default.
  - Named labels: xbyak uses L("name"), rxbyak uses asm.named_label("name").
  - lea_label(reg, &label) replaces xbyak's mov(reg, label) for
    getting code addresses (generates lea reg, [rip + disp32]).

Why: Rust's ownership model makes it impractical for labels to hold
back-references to the assembler. Opaque handles avoid lifetime issues.


11. STACKFRAME: EXPLICIT close() INSTEAD OF RAII
--------------------------------------------------
xbyak uses C++ RAII — the destructor emits the epilogue automatically:

  {
      StackFrame sf(code, pNum, tNum, stackSize);
      // ... function body ...
  }  // destructor emits epilogue

rxbyak requires an explicit close() call:

  let sf = StackFrame::new(&mut asm, 2, 1, 0)?;
  // ... function body ...
  sf.close(&mut asm)?;    // consumes sf, emits epilogue

close() takes self by value, preventing double-close at compile time.

Why: Rust's Drop trait cannot borrow &mut CodeAssembler because the
StackFrame cannot store a mutable reference with the required lifetime.
Additionally, Drop::drop() cannot return Result, making error propagation
from the destructor impossible.


12. COMPOSITION INSTEAD OF INHERITANCE
----------------------------------------
xbyak users inherit from CodeGenerator:

  struct MyCode : Xbyak::CodeGenerator {
      MyCode() {
          mov(eax, 42);   // 'this' is the assembler
          ret();
      }
  };

rxbyak always uses an explicit assembler instance:

  let mut asm = CodeAssembler::new(4096)?;
  asm.mov(EAX, 42)?;
  asm.ret()?;

Internally, CodeAssembler composes CodeBuffer + LabelManager rather than
inheriting from a base class.

Why: Rust has no class inheritance. Composition is idiomatic.


13. UNSAFE get_code()
----------------------
xbyak's getCode<T>() returns a function pointer directly.
rxbyak marks it unsafe:

  let f: fn(i64, i64) -> i64 = unsafe { asm.get_code() };

Why: Transmuting a byte buffer into a function pointer is inherently
unsafe. The caller must ensure the generated code matches the declared
function signature. Rust makes this responsibility explicit.


14. ready() COMBINES LABEL RESOLUTION + MEMORY PROTECTION
-----------------------------------------------------------
xbyak requires separate calls for finalizing code:
  setProtectModeRE() or readyRE()

rxbyak combines both into a single ready() call that:
  1. Checks for undefined labels
  2. Resolves AutoGrow jump addresses
  3. Sets memory protection to RX (read+execute)

Finer-grained control is still available via ready_re(),
set_protect_mode_re(), and set_protect_mode_rw().


15. BUILD-TIME CODE GENERATION
-------------------------------
xbyak defines all ~1400 instruction methods manually in header files.

rxbyak uses a build-time code generation system (build.rs) that reads
instruction tables from gen/instructions.rs and gen/avx512.rs, then
generates method implementations into mnemonics.rs. This eliminates
thousands of lines of boilerplate.

~280 instructions with complex encoding logic (GPR, jumps, bidirectional
moves, x87, opmask, AMX) are hand-written in assembler.rs and listed in
the HANDWRITTEN array to skip code generation.

This approach is unique to rxbyak; xbyak does not use code generation.


16. TypeFlags NEWTYPE
----------------------
xbyak uses raw integer constants for encoding flags (T_66, T_F2, T_0F, etc.).
rxbyak wraps them in a newtype struct:

  pub struct TypeFlags(pub u64);

  pub const T_66: Self = Self(1 << 5);
  pub const T_F2: Self = Self(1 << 6);

The struct implements BitOr, BitAnd, etc. for combining flags.
Bit positions match xbyak exactly for ease of porting.

Why: A newtype prevents accidentally mixing TypeFlags with raw integers.


17. MISSING / NOT PORTED FEATURES
-----------------------------------
- 32-bit mode (XBYAK32): Not supported
- XBYAK_USE_MEMFD: memfd-backed executable memory not implemented
- XBYAK_ENABLE_OMITTED_OPERAND: VEX 2-op shorthand (dst implied) not
  supported; all operands must be explicit
- Custom allocators: xbyak supports custom allocators via template
  parameter; rxbyak uses the platform module directly
- cmpsd string operation: Missing (cmpsb/cmpsw/cmpsq exist, but cmpsd
  string would conflict with SSE cmpsd, like movsd/movsd_string)


18. PLATFORM ABSTRACTION
--------------------------
xbyak uses #ifdef _WIN32 / __linux__ preprocessor guards.
rxbyak uses Rust cfg attributes: #[cfg(unix)] and #[cfg(windows)].

Backend implementations:
  - Unix:    libc::mmap / munmap / mprotect
  - Windows: VirtualAlloc / VirtualFree / VirtualProtect

Drop on CodeBuffer automatically frees executable memory, but silently
ignores errors (let _ = ...) since Drop cannot propagate Result.


19. REGISTER EQUALITY EXCLUDES EVEX MODIFIERS
-----------------------------------------------
Reg's PartialEq compares only idx, kind, and bit — deliberately excluding
mask, rounding, zero, nf, and zu. This means:

  XMM0.k(1) == XMM0    // true

This matches how xbyak compares base register identity.


20. OPERAND POLYMORPHISM VIA Into<> TRAITS
--------------------------------------------
xbyak uses C++ implicit conversions to accept Reg, Address, or immediate
values in the same parameter position.

rxbyak uses enum types with Into<> trait bounds:

  pub enum RegMem { Reg(Reg), Mem(Address) }
  pub enum RegMemImm { Reg(Reg), Mem(Address), Imm(i64) }

  pub fn mov(&mut self, dst: impl Into<RegMem>, src: impl Into<RegMemImm>)

From trait implementations enable automatic conversion:
  impl From<Reg> for RegMem { ... }
  impl From<Address> for RegMem { ... }
  impl From<i32> for RegMemImm { ... }

Why: Rust has no implicit conversions. The Into trait pattern is the
idiomatic equivalent, providing compile-time safety while keeping the
API ergonomic.


21. PARITY AUDIT BASELINE (2026-08-23)
---------------------------------------
Reference checkout:

  Xbyak v7.40, commit 1230a6cedabdce6fe0246e5324232451f90ac300

The checked-in tools/audit_xbyak.py script evaluates Xbyak's preprocessor
surface for rxbyak's supported configuration (XBYAK64, AVX-512 enabled,
optional omitted-operand overloads disabled) and reports:

  Xbyak active 64-bit mnemonic names:           1879
  Xbyak active 64-bit mnemonic overloads:        2439
  rxbyak handwritten public instruction methods: 791
  rxbyak generated unique methods:              1002
  Xbyak names matched after Rust API mapping:    1669
  Xbyak names not matched:                        210
    compatibility aliases with existing encoder:   0
    missing encoder/API names:                    210

The tool excludes the 32-bit-only branch instead of mixing it into the queue.
It separately identifies direct Xbyak forwarders and known spelling aliases.
All 178 such names now have public Rust wrappers: 160 SSE/AVX compare-predicate
names, eight PCLMULQDQ names, six conditional-jump spellings, SAL, WAIT, PUSHFQ
and POPFQ. The remaining 238 names require an encoder or public API audit.
Conversely, a matched name does not prove that every Xbyak overload or
validation rule is present. Operand-form and byte-level parity must therefore
still be reviewed family by family.

The original rxbyak import was made while Xbyak v7.33.3 was current. Between
v7.33.3 and v7.40, upstream added 39 unique mnemonic names and removed eight.
The first synchronization slice has:

  - ported prefetchrst2 and pushp/popp;
  - ported the 10-15 byte NOP table and the new default NOP mode;
  - aligned the complete prefetch family and its memory-size validation;
  - removed the six retired Xeon Phi methods that rxbyak still exposed;
  - ported Xbyak 7.39 reset ordering, including RX-to-RW restoration and
    clearing pending relocation state before reusing a code buffer;
  - ported the ACE 1.15 BSR0 register and bsrinit/bsrmovf/bsrmovh/bsrmovl;
  - ported the ACE 1.15 tilemovcol and TOP2/TOP4 AMX instruction families;
  - ported the ACE 1.15 FP8 conversion families, vpmovssdb and vunpackb;
  - confirmed the emitted bytes directly against Xbyak v7.40.

All 39 unique mnemonic names added between v7.33.3 and v7.40 now have rxbyak
counterparts, and all eight names removed upstream are absent. The wider
pre-v7.33.3 unmatched set still needs classification and operand-form review;
this document no longer claims that the existing instruction list proves full
Xbyak parity.

The first non-mnemonic parity slice also ports Xbyak 7.35-7.37 behavior for a
null RIP target (`RegExp(0)` is an integer displacement), bounds-checks the
entire `CodeArray::rewrite` range, exposes `Address::changeBit`, and adds the
previously absent `CodeGenerator::putSeg` counterpart. Segment-prefix tests use
the exact byte sequence from Xbyak's upstream regression test.

The Xbyak 7.39.1 EGPR review found that rxbyak's existing `vpextrw` method had
the ModR/M operands reversed and accepted only a register destination. It now
matches upstream's compact VEX path for low registers and its 0F3A path for
memory or r16-r31 destinations. The same slice ports all five `vmovq` overload
families and the four `opCvt3` scalar conversion families, retaining GPR kind
through EVEX so B4 selects r16-r31 correctly. Tests assert bytes generated by
Xbyak v7.40.

The encoder-validation slice ports the Xbyak 7.35.4 `disp8*N` correction for
`vcvt2ph2{b,h}f8[,s]` and `vcvthf82ph`, including the corrected F2/map flags.
It also ports Xbyak 7.37.6's common `opVex` rejection of `{z}` when `T_M_K`
marks a memory destination. Both behaviors have focused regression tests; the
disp8 expected bytes were generated directly with Xbyak v7.40.

The compatibility-alias slice reproduces Xbyak's 32-entry compare-predicate
table and four-entry PCLMULQDQ table in rxbyak's existing build-time generator.
Because Rust cannot overload the vector-result and opmask-result VCMP methods,
the four base methods dispatch on the destination register kind; this also fixes
the previous generator behavior that silently discarded the AVX-512 overloads
as duplicate names. Exact bytes for VEX XMM/YMM and EVEX K/XMM/YMM/ZMM base
forms were generated with Xbyak v7.40 and checked in as regressions. The tests
also exercise every one of the 160 compare aliases; all 128 AVX aliases are
checked with both vector and opmask destinations. All eight PCLMUL aliases are
covered as well.

The Xbyak 7.37.2 user-wait slice ports `tpause`, `umonitor`, and `umwait`.
Unlike rxbyak's previously absent API, these use the shared register encoder,
so r8-r31 receive REX/REX2 exactly as upstream intended. The regression test
covers 16/32/64-bit `umonitor` and low/EGPR forms with Xbyak-generated bytes.

Before porting Xbyak 7.38 `StackFrame`, its missing APX prerequisite was ported
as a separate slice: the upstream-owned `evexLeg` and `opROO` helpers plus
`push2`, `push2p`, `pop2`, and `pop2p`. Exact-byte tests cover ordinary
callee-saved registers and r30/r31 with PPX hints against Xbyak v7.40.

The following StackFrame slice ports the complete Xbyak v7.40 register and
vector flag surface: UseRBP/RCX/RDX/RSI/RDI/R30R31,
UseRBPAsFramePointer, UsePUSH2, UsePPX, UseSSE(n), UseAVX(n), and
NoVzeroupper. Register-slot substitution, caller/callee-save accounting,
prologue/epilogue ordering, stack alignment, APX paired pushes, vector flag
validation, and the Win64 XMM6-15 save-area logic follow xbyak_util.h. The one
intentional API difference remains section 11's explicit consuming close();
close_with_ret(false) is the Rust counterpart of close(false).

On Linux, a differential corpus compared all 9,052 prologue/epilogue byte
sequences generated by rxbyak with Xbyak v7.40: 6,560 GPR/stack combinations,
92 SSE/AVX combinations, and 2,400 APX stack combinations. Every sequence
matched. Focused checked-in tests retain representative exact-byte cases and
the upstream vector-flag rejection matrix. The Win64 path was reviewed
line-by-line against the same source; it remains target-gated and requires a
Windows test run for byte-level execution evidence.
The Win64 implementation and tests type-check with
`cargo check --target x86_64-pc-windows-gnu --tests`; the local environment
does not provide the MinGW linker needed to execute or link that test target.

The Cpu slice now follows Xbyak v7.40 through feature ID 101. It adds
AMX_COMPLEX, ACE, AVX10_V1_AUX and AVX10_V2_AUX detection, tile-palette and
ACE-version queries, the AVX10 auxiliary subleaf, and Xbyak's guarded 0x1e
subleaf traversal. Feature constants retired by upstream (the Xeon Phi
AVX-512 groups, PREFETCHWT1, and AMX_TRANSPOSE) are no longer exposed or set.
The Apple on-demand AVX-512 rule and Intel cache SMT-width update also match
the current C++ ordering. Public CPUID/XFEATURE helpers and fallible cache/core
queries cover the remaining Cpu API surface using Rust Result in place of
Xbyak exceptions. A native differential probe compared all feature bits
0-101, family/model fields, topology counts, every data-cache entry, and the
three version/palette values with Xbyak v7.40; all values matched on the audit
host. CpuTopology remains a separate structural/platform audit slice.

CpuMask is now an owned topology type rather than a raw BTreeSet field. Its
monotonic append contract, 0-1023 index range, inclusive ranges, strict list
parser, iteration and canonical range serialization follow Xbyak. rxbyak uses
the BTreeSet-backed implementation that upstream itself selects with
XBYAK_CPUMASK_COMPACT=0 rather than reproducing the default 64-bit packed
storage; no CpuMask bytes cross an ABI or serialization boundary. Rust Result
reports the same invalid-index conditions that Xbyak reports by boolean return
or exception. The platform-specific CpuTopology population remains the next
slice.

CpuTopology's common API and Linux population now follow Xbyak v7.40. The
constructor derives hybrid state from Cpu and returns CantInitCpuTopology on
failure; LogicalCpu/CpuCache expose the upstream sibling, cache and diagnostic
helpers. Linux uses `_SC_NPROCESSORS_ONLN`, scans the same four cache indices,
assigns the same sysfs fields, and restores the original affinity after the
CPUID 0x1a hybrid-core fallback. A native differential probe compared the
top-level counts/line size/hybrid flag and every logical CPU's core ID, core
type, four cache size/associativity pairs and sharing masks; every value
matched Xbyak v7.40 on the audit host. macOS remains intentionally unsupported
because upstream also returns initialization failure there.

The Windows topology slice now mirrors Xbyak's three
GetLogicalProcessorInformationEx passes: RelationGroup builds the processor
group accumulators, RelationProcessorCore assigns physical-core IDs and hybrid
efficiency classes, and RelationCache populates the four cache slots and their
sharing masks. The Rust parser validates each variable-sized relationship and
its flexible arrays before dereferencing them; this is a memory-safe adaptation
of Xbyak's pointer walk and does not alter accepted OS data. As in Xbyak's
conservative build when NTDDI_VERSION is absent, cache relationships use the
legacy single GroupMask. The implementation and its Windows-only contract test
type-check with `cargo check --target x86_64-pc-windows-gnu --tests`. This audit
host has neither Wine nor a MinGW linker, so native Windows runtime/differential
execution remains pending and is not claimed as verified.

The system/control-instruction slice ports 38 previously missing active
mnemonic names from xbyak_mnemonic.h: CLZERO, CET indirect-branch markers,
MONITOR/MWAIT variants, MSR/performance-counter access, SERIALIZE, SMAP,
system-call entry/return, cache write-back, RTM, XGETBV/XLATB, load-address
tracking, user interrupts, RDRAND/RDSEED, FSGSBASE, SENDUIPI, CLDEMOTE, CLWB,
and MOVRS. Rust keeps Xbyak's generic Reg acceptance for RDRAND/RDSEED and
MOVRS rather than imposing a narrower GPR-only policy. Representative
low/extended/EGPR registers, complex addresses, every zero-operand byte string,
and the MOVRS REX2 rejection were generated directly with Xbyak v7.40 and are
checked in as exact-byte regressions.

That comparison exposed a shared encoder divergence: rxbyak's memory-form REX
path only emitted operand-size override for a 16-bit register when the memory
operand had an explicit size. Xbyak emits 0x66 for an unsized memory operand as
well. The p66 condition now follows xbyak.h::rex literally; MOVRS AX is the
focused regression. CLFLUSH and CLFLUSHOPT also carry Xbyak's
T_ALLOW_DIFF_SIZE flag again. No binary-layout-bearing type changes in this
slice.

The legacy-control slice ports IN/OUT and string OUTS, INT, RETF, LFS/LGS/LSS,
LOOP/LOOPE/LOOPNE, JECXZ/JRCXZ, and APX JMPABS. `op_load_seg`, the port-I/O
validation helpers, and the short-only label path remain in assembler/encoder
ownership corresponding to xbyak.h rather than a generic instruction table.
Rust represents C++ overloads as `in_`/`in_imm`, `out_`/`out_imm`, and
`retf`/`retf_imm`; `loop_` escapes the Rust keyword. Existing Label handles are
used instead of duplicating Xbyak's string-label overloads. Forward and
backward branches, too-far binding, all legal accumulator widths, invalid port
registers, low/extended/EGPR segment loads, and immediate byte order match
Xbyak v7.40 differential output.

The same re-read found that `ret_imm(0)` did not honor Xbyak's `if (imm)`
selection and emitted C2 0000 rather than C3. Both RET and RETF immediate Rust
entry points now select the no-immediate opcode for zero exactly as upstream.
NASM intentionally encodes the textual `ret 0` as C2 0000, so that one case is
covered by the Xbyak-specific regression rather than the NASM comparison set.
No binary-layout-bearing type changes in this slice.

The x87-state slice ports FBLD/FBSTP, FIDIVR/FISUBR, FLDENV, FNSAVE/FNSTENV,
FRSTOR, FSAVE/FSTENV/FSTSW, FSINCOS, and FXRSTOR/FXRSTOR64. The new
`fpu_mem_by_size` helper is the direct Rust counterpart of xbyak.h `opFpuMem`:
it selects the escape byte from the Address width, applies the alternate m64
extension, rejects unsized/unsupported memory, and preserves address-prefix
ordering. Existing explicit-width x87 entry points remain available; the two
new reverse-integer methods expose upstream's size-driven API. Rust keeps the
AX-only FSTSW register contract as `fstsw_reg`, with `fstsw` owning the memory
overload because Rust has no method overloading.

Exact-byte regressions cover WAIT versus FN forms, low and extended complex
addresses, the REX.W-only distinction of FXRSTOR64, invalid unsized integer
memory, and the AX validation. Every expected sequence was generated with
Xbyak v7.40. No binary-layout-bearing type changes in this slice.

Before the MMX interoperability slice, the shared legacy-SSE encoder now ports
xbyak.h `isValidSSE` ordering inside `opSSE`: after family-specific operand
validation and before `opRO`, either operand being XMM16-XMM31 returns
NotSupported. Both destination and source rejection paths were confirmed with
a Xbyak v7.40 probe and are retained as focused regressions. Store helpers that
do not route through `op_sse` are outside this helper-specific prerequisite and
remain subject to their own operand-form audit. No binary-layout-bearing type
changes in this slice.

The MMX-interoperability slice ports CVTPD2PI/CVTPI2PD/CVTPI2PS/CVTPS2PI,
CVTTPD2PI/CVTTPS2PI, MASKMOVDQU/MASKMOVQ, MOVDQ2Q/MOVQ2DQ, MOVNTQ, and
PSHUFW. The three operand-family predicates remain direct counterparts of
xbyak.h `isMMX_XMMorMEM`, `isXMM_MMXorMEM`, and `isXMMorMMX_MEM`; validation
therefore occurs before the shared `op_sse` XMM16 check in the same order as
upstream. Register, extended-register, complex-memory, immediate, invalid-kind,
mixed MMX/XMM, and XMM16 cases match Xbyak v7.40 differential output.

PSHUFW deliberately retains Xbyak's generic Mmx hierarchy behavior: matching
XMM operands are accepted and use the unprefixed opcode, while mixed XMM/MMX
operands are rejected. No binary-layout-bearing type changes in this slice.

Before porting MOVBE/MOVDIRI/MOVDIR64B, `CodeBuffer::op_mr_alt` now mirrors the
optional `type2`/`code2` branch of xbyak.h `opMR`. It invokes the existing
upstream-owned `op_roo`/`evexLeg` path first and falls back to legacy `op_mr`
only when no APX/REX2 state requires the alternate form. Rust makes `code2`
explicit instead of representing Xbyak's internal NONE sentinel. A focused
unit test compares the legacy r8d and APX r16d MOVDIRI encoder paths against
Xbyak v7.40 bytes. The public consumers are included in the same warning-free
commit after this prerequisite was independently verified.

MOVBE load/store, MOVDIRI, MOVDIR64B, and MOVNTDQA now expose that behavior.
Differential tests cover both MOVBE directions, legacy r8-r15 and APX r16-r31,
MOVDIR64B's exact `cvt32` behavior, MOVNTDQA's XMM16 rejection, and Xbyak's
otherwise permissive derived-register behavior. No binary-layout-bearing type
changes in this slice.

The scalar APX/BMI slice ports xbyak.h `opRRO` without collapsing its encoding
choice: operand widths are checked first, W follows the destination, classic
registers use VEX, and EGPR or destination-NF state uses `opROO`/EVEX-legacy.
The RegMem `has_rex2` query intentionally excludes source NF/ZU, matching the
exact narrower predicate used by Xbyak's helper. The pre-existing RORX, SHLX,
SHRX, SARX, ANDN, BEXTR, BZHI, PDEP and PEXT methods now route through this
helper too; this restores their APX/EGPR forms and ANDN/BEXTR/BZHI NF support.

RAO-INT AADD/AAND/AOR/AXOR, ADCX/ADOX, BLSI/BLSMSK/BLSR and MULX are now
public. Rust exposes Xbyak's overloaded three-operand ADCX/ADOX forms as
`adcx3`/`adox3`; all methods remain in the mnemonic-owning assembler module.
Exact-byte regressions generated with Xbyak v7.40 cover legacy, VEX, APX,
EGPR, NF, register, memory, immediate and invalid-width paths. No
binary-layout-bearing type changes in this slice.

The Key Locker slice ports xbyak.h `opEncodeKey` and `opSSE_APX` in encoder
ownership, then exposes all AESENC/AESDEC 128/256 and wide forms plus
ENCODEKEY128/256. ENCODEKEY preserves Xbyak's exact threshold: r0-r7 use the
legacy F3.0F38 opcode, while either operand at r8 or above selects the EVEX
form. Key Locker AES uses legacy SSE for ordinary addresses and EVEX-legacy
only when the address itself requires REX2.

The post-port source re-read also preserves an unusual upstream consequence
of `opSSE_APX` ordering: YMM/ZMM objects passed through Xbyak's Xmm base class
are rejected on the legacy fallback, but are encoded when an EGPR address
takes the APX branch before `isXMM_XMMorMEM` validation. Focused regressions
cover that distinction, every public mnemonic, XMM16 rejection, both address
paths and the four ENCODEKEY register thresholds. No binary-layout-bearing
type changes in this slice.

The MPX slice ports BND, BNDCL/BNDCN/BNDCU, BNDLDX/BNDSTX, BNDMK and both
BNDMOV directions. Rust names the memory-destination overload
`bndmov_store`; the load/register form retains `bndmov`. The encoder-owned
`op_mib` counterpart enforces ModRM addressing and disables Xbyak's
`[reg*2]` optimization exactly where MPX MIB requires the unmodified SIB.

MPX register checks also use the `disableRex` branch of xbyak.h `opRext`:
64-bit registers and explicitly sized m64 operands are converted to the
32-bit encoding width before prefix selection. Differential bytes cover
32/64-bit and extended registers, sized and unsized memory, BND-register
moves, optimized versus non-optimized `[rax*2]`, and RIP rejection. No
binary-layout-bearing type changes in this slice.
